## Success-criteria evidence

- **SC-009:** The representative public storefront performance gate remains recorded in `us1-performance-evidence.md`. The hosted-payment journey adds no client-side provider secret and renders the authoritative return state through the optimized server build. A deployed p75 measurement remains a launch gate because local fixture latency cannot represent TBC or public-network latency.
- **SC-010:** The local two-Manager browser journey completed all staff mutations and rerenders in 3.4 seconds total, while database queue and reconciliation operations remain indexed and bounded. The production/staging 95th-percentile admin-list run remains part of the final deployment gate.
- **SC-015:** From the admin landing page, an operator reaches an exception filter in one action and an individual order in the second; direct safe-reference search also reaches it within two actions.
- **SC-018:** Failed provider events, stale pending payments, failed notices, transfer mismatches, dead letters, and fulfillment work appear as privacy-safe dashboard counts/queue references linked to their recovery surface. Scheduled reconciliation retries the recoverable classes and raises durable alerts when bounded retries are exhausted.

## Activation boundary

This phase is operationally complete with local fixture providers. Public launch still requires rotated Supabase credentials, live TBC merchant credentials and callback allow-list confirmation, a verified Resend domain, Owner-approved Georgian bank instructions, production delivery settings, and staging/production performance evidence. Fixture payment and email modes are rejected when `DEPLOY_ENV=production`.
